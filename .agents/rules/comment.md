# コメントに関するルールや考え方

## 全般

- 自明な処理にコメントしない（コード・型・命名から読み取れることは書かない）
- 既存のコメントを破壊しない
- この変更・この差分に固有の経緯（「従来は」「今回」「〜を外した」等）を書かない（コードの最終的な読み手はその経緯を知らない）
- コメントの量はその影響範囲、つまりどれだけ多くの場所から呼び出されるかに依存する
  - 他の場所から呼び出されうる定数・関数は丁寧に説明する
  - 関数は JSDoc に近い書き方を心がける

## コメントを追加する前に必ず注意するべきこと

コメントを 1 行でも追加するときは、以下の 3 つをすべて満たすことを確認する。
ひとつでも満たさないなら、そのコメントは書かない。

1. **言い換えでない**：直下のコード・直上の既存コメントを日本語に翻訳しただけではないか
2. **初見で必要**：この差分・その背景にある会話・関連するレビューなどの文脈を一切知らない人が、3 ヶ月後にこのファイルだけを開いたときに必要な情報か
3. **コードに書けない**：命名・型・構造で表現できない情報か（表現できるなら、コメントを足すのではなくコードを直す）

## ではどこに書けばいいのか

先の条件をひとつでも満たさないような場合、その内容は以下のような場所に昇華することを検討する。

| 内容                                              | 行き先                              |
| ------------------------------------------------- | ----------------------------------- |
| なぜこの変更をしたか・何が問題だったか            | PR の本文・コミットメッセージの本文 |
| レビュー指摘への対応内容                          | PR のコメント                       |
| 設計判断・複数ファイルにまたがる背景              | `docs/` 配下のドキュメント          |
| どうしてもコードと 0 距離で結びついているべき情報 | これはコメントとして書いてよい      |

## コメントの例

### 型定義

```typescript
// src/types/user.ts

/**
 * 配送先住所
 *
 * - id           : 住所の一意識別子
 * - postalCode   : 郵便番号
 * - fullAddress  : 住所
 * - recipientName: 受取人名
 * - isDefault    : デフォルト住所かどうか
 */
export type Address = {
  id: string;
  postalCode: string;
  fullAddress: string;
  recipientName: string;
  isDefault: boolean;
};
```
